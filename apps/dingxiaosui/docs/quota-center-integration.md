# 丁小穗与发卡网实际接入说明

更新：2026-10-30。本源码已增加发卡中心接入，保留丁小穗现有页面、业务提示词、知识库、作品和旧活动卡。本文描述仓库实现；开发者需要配置自己的发卡中心、上游渠道与部署环境。

## 客户流程与次数规则

客户在发卡网选择文案、图片、视频次数组合，付款经发卡网确认后，在手机订单页获取 `QTA-…` 激活码，再到丁小穗原激活窗口粘贴。每张卡对应一份独立作品空间；同一码重新登录或换设备会恢复原空间和余额，不再次充值。切换不同卡会切换空间，不合并其他卡的作品。

例如 `{text:3,image:1,video:1}` 表示文案 3 次、图片 1 张、视频 1 个。三项可自由组合，包括某项为 0；总次数 5 只是汇总，不能把剩余图片次数当作文案使用。新卡余额由发卡中心维护，丁小穗不再另扣一份本地活动次数。历史共享次数另行显示：某项调用先用对应次数，不足部分可用共享次数，不能借用另一项的独立次数。

文案保留原结构化提示词和知识库输入；图片支持文字生图及上传图片改图；图片、视频异步完成后由丁小穗后端保存到自己的媒体存储。新接入视频当前按 5 秒配置；旧活动卡原有 15 秒服务保持不变。新卡不套用旧活动批次或 7 天有效期。

## 启动配置

以下变量只注入丁小穗服务端进程，不放到前端构建变量、网页或仓库：

| 变量 | 用途 |
| --- | --- |
| `QUOTA_CENTER_URL` | 丁小穗后端可访问的发卡中心根地址，也接受以 `/api/v1` 结尾的地址 |
| `QUOTA_PLATFORM_KEY` | 发卡网中 `dingxiaosui` 业务平台的接入凭证；不是 APIMart 密钥，也不是发卡网管理员凭证 |
| `SHOP_PRODUCT_URL` | 客户浏览器可打开的商品页，例如 `https://发卡网域名/?service=dingxiaosui-creator` |

仅在这两个服务运行于同一台电脑时，`QUOTA_CENTER_URL` 可以使用 `http://127.0.0.1:3199`。手机、另一台电脑或线上丁小穗不能用这个地址访问本机发卡网。部署时应配置可达的服务地址，并同步设置发卡中心允许的域名、反向代理与公开商品地址；不要用放宽鉴权或全开放 CORS 代替正确配置。

本地活动版沿用：

```sh
node scripts/local-handoff.mjs build
node scripts/start-event-preview.mjs --port 8845
```

先向启动进程注入上表变量，再启动。`start-event-preview.mjs` 不读取 `.env` 文件，但会继承 `QUOTA_CENTER_URL`、`QUOTA_PLATFORM_KEY`、`SHOP_PRODUCT_URL`。它自动设置本地 `APP_ENV=production`、`APP_ORIGIN`、`PASSWORD_AUTH_ENABLED=1`、`EVENT_ACTIVATION_ENABLED=1`、`ZLG_GATEWAY_REQUIRED=0` 和 `MEDIA_BACKGROUND_ENABLED=1`，并使用 `.local-event-runtime/config.json` 中已有主密钥。

发卡网根目录的统一准备／启动入口由发卡网项目维护；已有联动配置时优先按它的 README 启动，避免在两个终端创建不同运行目录或重复占用端口。

## 数据迁移与身份

新增 `drizzle/0017_quota_center.sql`，创建 `quota_center_accounts` 和 `quota_center_sessions`，不重建或清空旧卡表。启动脚本通过 `scripts/migrate-ecs.mjs` 按顺序执行尚未应用的迁移；在已有生产环境升级时，先针对原数据目录制作一致性备份，再执行同一迁移流程。

本地身份表保存卡密 HMAC、稳定的本地用户 ID、稳定的中心用户 ID、兑换结果和处理状态。完整卡密不入库、不写日志。卡密 HMAC 与媒体请求加密依赖原有 `AI_CONFIG_ENCRYPTION_KEY`：必须保留数据和主密钥配对，不能为本次升级重置密钥。保留原线上账号、作品、活动批次和供应商配置；不要用本机数据库覆盖线上数据库。运行中的 SQLite 应用备份能力或一致性快照，不能只复制正在写入的主数据库文件而遗漏 WAL。

新会话使用原 `zdx_event_session` 的 HttpOnly Cookie，但从独立新表查询，身份类型为 `quota_center`；用户身份从服务端会话推导，不相信浏览器提交的用户 ID、工作区 owner 或角色。管理员切换需原有明确操作，先验证卡码，再撤销当前管理员会话；新卡永远不获得管理员权限。

## 兑换与生成接口

丁小穗调用发卡中心的正式服务端接口：

| 操作 | 接口 |
| --- | --- |
| 激活 | `POST /api/v1/redeem`，`{userId,code,idempotent:true}` |
| 余额 | `GET /api/v1/balance?userId=…` |
| 生成 | `POST /api/v1/generate`，固定服务端用户、能力和防重复请求 ID |
| 查询 | `GET /api/v1/generation/{id}?userId=…` |
| 保存媒体 | `GET /api/v1/generation/{id}/content?userId=…&index=0` |

中心根据平台凭证选择平台及对应 API 渠道、模型；客户不能通过请求指定其他渠道或上游密钥。所有调用只从丁小穗后端发送，媒体下载也由后端鉴权、保存后向所属用户提供。

首次激活先持久保存 `pending` 映射，再兑换，短租约阻止并发重复处理。发卡中心现在支持显式 `idempotent:true`：同一卡、同一平台、同一个中心用户可返回原回执，不增加余额；其他用户仍返回冲突。因此之前“首次兑换响应丢失无法确认”的限制已解决：用原卡和原持久身份重试即可恢复。默认未设置该选项的中心兑换行为不变。

生成任务也使用固定防重复请求 ID；同 ID 同内容重试返回原任务，改变内容会冲突。中心负责预留、成功结算和明确失败返还，丁小穗不再外层调用另一套预留／扣次。媒体提交前保存加密原请求，收到中心任务 ID 后清除临时原请求；刷新、重启或保存失败只恢复原任务，不重新生成。

## 故障处理

| 现象 | 处理 |
| --- | --- |
| 激活正在处理／网络超时 | 稍后重新提交原卡；保留 `pending` 记录及稳定用户 ID，不删除映射后重建用户 |
| 卡码归属需核对，状态 `review` | 管理员核对中心卡密归属、平台、付款交付状态及本地映射；不能凭当前余额或一个 409 响应认领卡码 |
| 接入凭证或地址错误 | 管理员修复服务端配置；不用客户填写 API 密钥，也不要让客户重复付款 |
| 某项次数不足 | 先查看该项和共享余额；另一项有余额不代表当前项可用 |
| 生成 `queued`／`running` | 等待并查询原任务，不能新建相同生成 |
| 生成 `uncertain`／结果待核对 | 次数仍预留，管理员核对上游任务或账单后在中心处理，不先退款再重跑 |
| 已生成但作品保存失败 | 重试原任务下载与本地保存，不再调用生成；保存完成前保留原渠道配置 |
| 文案 JSON 已返回但业务内容校验失败 | 中心保持待交付且未扣次；丁小穗拒绝后自动退回，同一请求重试不会再次调用上游 |

新卡只从中心取得额度和模型服务；服务暂不可用时明确报错，不切回旧体验卡额度或隐式付费备用模型。旧 `ZDXE-…` 码继续走原独立活动逻辑，原次数、有效期、批次与作品不受新卡接入影响。

## 验证范围

已新增隔离验证 `node scripts/test-quota-center-identity.mjs`，覆盖 3／1／1 余额、并发激活、丢兑换响应、同码恢复、归属冲突、管理员切换及会话隔离；旧 `test-event-sessions.mjs`、`test-event-auth.mjs` 仍可运行。生成相关隔离验证由本轮生成模块测试和发卡网根目录的跨系统 HTTP 验收补充。

测试与本地启动不等同于真实收款或公网更新。真实付款以发卡网已配置的收款方式核验，客户自行点击“已付款”不能成为到账依据；实际收费生成和线上部署需按明确授权执行，并分别记录其结果。
